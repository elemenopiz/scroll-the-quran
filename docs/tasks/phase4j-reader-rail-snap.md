# Phase 4j — The verse rail must never leave the reader between pages
Owns: `Packages/ScrollKit/Sources/FeatureReader/{VerseRail.swift,VerseRailGeometry.swift,ReaderView.swift,ReaderModel.swift,ReaderPagination.swift,ReaderMetrics.swift}`, `UITests/ReaderTests.swift`, `UITests/Specs/reader-*.json`, tests. Simulator: whichever of `ScrollSim-3d` / `ScrollSim-3e` the orchestrator assigns in the prompt.

Owner's report (2026-09-12, with a screenshot): "the slider on the left doesn't work properly and drops you in between verses — this shouldn't happen." The screenshot shows Al-Baqarah 2:120 in the top half and the next page's Arabic + English rising from the bottom, with the toolbar drawn over the page text: the pager's content offset is parked mid-page after a rail scrub.

Cause (read `VerseRail.swift` lines 40–52 and `ReaderView.swift` lines 73–100): `DragGesture.onChanged` calls `onScrub(rail.ayah(atY:))` on every tick, which sets `ReaderModel.currentPageID`, which is bound to `.scrollPosition(id:)` on a `.scrollTargetBehavior(.paging)` scroll view. Dozens of programmatic position changes per second into a paging scroll view interrupt each other and the final one can settle between snap points; `onCommit` does not re-assert.

Deliver:
1. **Scrub without scrolling.** While the finger is down, the rail updates only its own state (`scrubAyah`, the number bubble, haptic ticks) and a lightweight preview — the surah:ayah label under the rail or a small floating card — and does NOT touch `currentPageID`. On release (`onEnded`), set `currentPageID` exactly once, inside `withAnimation(nil)` or a `Transaction` with animations disabled, then re-assert it on the next run loop (`Task { @MainActor in … }`) so the paging behavior snaps to the target even if a prior programmatic scroll was still in flight. If SwiftUI still parks between pages in testing, fall back to `ScrollViewReader.scrollTo(id, anchor: .top)` for the commit while keeping the binding for reads.
2. **Never mid-page.** Add a guard in `ReaderModel`/`ReaderView`: whenever `currentPageID` changes programmatically (rail commit, surah picker, deep link, random ayah, "jump to ayah" toast), the same double-set is used; add a `ReaderPagination` unit test for id→ayah→id round trips, and an XCUITest (`ReaderTests`) that scrubs the rail from ayah 1 to ~120 of Al-Baqarah with `press(forDuration:thenDragTo:)`, releases, then asserts the visible page's `reader.verse` label is exactly one ayah (2:N) and the page's frame is aligned to the pager (y of the verse page == y of the pager, tolerance 2 pt) and the toolbar does not overlap the text (verse text frame minY > toolbar maxY).
3. **Long-page ayat.** A scrubbed ayah that spans continuation pages lands on its first page (the "(1/3)" caption) — test 2:282.
4. **Rail geometry**: verify `VerseRailGeometry.ayah(atY:)` is monotonic and clamps at both ends; the top and bottom numbers stay legible; the current-number bubble does not overlap the toolbar or the tab bar at ayah 1 and ayah N (`reader-dark` snapshot must not move; RMSE unchanged to 4 decimals).
5. Gate: `SCROLL_SIM=… SCROLL_CAPTURE_SETTLE=6 Tools/verify.sh --ui --snap reader-dark reader-light` PASS.

DoD: rail scrub always ends on a page boundary (XCUITest proves it 5 times in a loop at random targets), no snapshot change, all reader tests green, sim shut down.
